The image domain pack ships as a built-in reference pack but all Civitai/Comfy/image logic must be reachable from core only through `domain_pack_manifest.json` and the generic domain-pack interface. Future non-image domain packs must be explicitly installed/registered, schema-validated, versioned, security-inventoried, and enabled by workspace or user config before core can load them. After registration, Q21 requires human-readable capability grants for provider/network access, file read/write roots, localhost UI, memory access, budget spend, and external tool/agent access; granted scopes are stored in the domain-pack registry plus workspace/user config, workspace settings can narrow user-level grants, and undeclared capabilities are denied by default. Under Q22, external packs run out-of-process through a JSON IPC/CLI worker contract; built-in packs may be bundled but must satisfy the same interface, and core passes only granted env vars, file roots, network/provider refs, and budget/memory scopes to the worker. Under Q23, workers do not perform provider calls, network access, file writes, budget spend, project memory writes, or external tool/agent calls directly; they emit typed side-effect requests, and core capability brokers enforce effective scopes, budget, credential refs, trace, output inspection, and evidence before performing the operation. Under Q24, every brokered side-effect request must carry `idempotency_key`, explicit `retry_policy`, `timeout`, `cancel_token`, and a terminal outcome; core records lifecycle events and never retries non-idempotent effects blindly. Under Q25, the core scheduler owns durable provider-job leases and polling; broker execution may return `pending` with a provider job ref, and `job_manifest.json`, `event_log.jsonl`, and `side_effect_result.json` store resume handles, lease owner, polling cadence, cancel token, and terminal outcome while workers remain stateless. Under Q26, active single-writer workspace/job lease holders are the only agents allowed to submit, poll, cancel, or finalize; stale leases recover after TTL with event-log evidence, and other agents see read-only status/resume surfaces until they acquire the lease. Under Q27, file-first workspace state is the first implementation source of truth; optional SQLite/Temporal adapters may exist later only if they export the same manifests. Under Q28, append-only event logs remain the audit source while periodic snapshot manifests carry schema version, event ranges, checksum chains, and migration-ledger references; compaction never silently deletes original events before final-package or handoff retention rules allow it. Under Q29, `serve-intake`, `serve-review`, and `resume` bind loopback-only by default, create random one-time session-token URLs with short TTLs, require CSRF tokens plus origin checks for mutating actions, keep static artifacts read-only unless the token grants an action, and still route saved actions through CLI/state lease checks. Under Q30, each host agent uses `agent_identity.json` or user-config identity with stable `agent_id`, session id, human-visible label, host/runtime/version, optional local signing key, and workspace grant status; unknown agents may read handoff/status but need explicit approval before lease acquisition or budget-spending mutation, and events, leases, broker requests, and UI confirmations record actor identity and trust state. Under Q31, workspace artifacts use retention classes: final packages and opt-in project memory persist until explicit deletion, handoff/status packages persist until superseded or finalized, event logs and snapshots persist until final-package/handoff retention permits compaction, raw intermediates/temp renders/provider caches are prunable only after reproducibility and handoff proofs exist, and deletions write tombstone events without ever storing raw secrets. Under Q32, host LLMs produce typed `decision_manifest.json` and `proposal_manifest.json` records while harness core stays deterministic; any harness-owned model call must be an optional brokered side effect with provider profile, budget, input hash, model id, output schema, trace, and evidence in `llm_call_manifest.json`. Under Q33, first implementation and QA are live-provider-first when provider credentials resolve; mocks/fixtures remain explicit fallback for missing credentials, forced offline mode, deterministic unit tests, and failure fixtures, but default executable demos should exercise the real provider path inside the approved budget, credential, actor-trust, lease, idempotency, and cleanup gates. Under Q34, every credential profile must declare hard live caps such as `max_live_smoke_spend`, `max_live_jobs`, wall-clock cap, and cleanup requirements; missing caps block live execution and open a setup/budget prompt, and the workspace budget envelope must fit inside the provider-profile cap rather than replacing it. Under Q35, default CI and PR checks stay mock/offline even when credentials and caps exist; live provider checks are manual, scheduled, label-gated, or env-gated runs that require provider-profile cap evidence and cleanup evidence, while local executable demos remain live-first. Under Q36, the first implementation must include a real second non-image production domain pack, not only a fixture or static boundary test; the exact domain is selected in Q37, and it must prove the same Skill/CLI/state/review/finalize/handoff lifecycle without Civitai, Comfy, image files, graph-patch taxonomy, or visual-gallery assumptions. The image pack proves the contract by importing existing Civitai/Comfy workflows when available, preserving the original graph, applying validated typed graph patches selected from a researched augmentation taxonomy, using localhost creator intake/review surfaces, and producing reproducibility packages. Product decisions must be expressed as reusable harness contracts before any Civitai/Comfy/image-specific behavior is accepted into the plan.

## Decisions (with rationale)
- Build a Cross-Agent Execution Harness, not an MCP server and not an image-generation app. Rationale: the durable value is a shared skill/CLI protocol, domain-pack contract, state machine, handoff, and loop semantics that can run under multiple agents.
- Treat image generation as reference domain pack 1. Rationale: Civitai/Comfy gives concrete workflows, visual review, paid execution, and artifact packaging pressure, but those details must validate the harness abstraction rather than define the product boundary.
- Harness-first reanchor is approved. Rationale: the user said "진행해" after the scope correction; continue from Cross-Agent LLM Execution Harness first, with image generation as reference domain pack 1.
- Ship the image pack as a built-in reference domain pack with a hard manifest boundary. Rationale: Q19 selected built-in delivery for first-version usability, but with `domain_pack_manifest.json` enforcement so core imports/calls only the generic pack interface and cannot directly depend on Civitai/Comfy/image internals.
- Register future non-image domain packs through manifest-first allowlist. Rationale: Q20 selected explicit install/register plus schema validation, versioning, security inventory, and workspace/user-config enablement before core can load a pack, preserving extensibility without arbitrary local-folder trust.
- Grant registered domain packs least-privilege capabilities. Rationale: Q21 selected explicit capability groups rather than all-or-nothing trust or per-action prompts; workspace-level narrowing preserves safety without breaking validation-pass autopilot.
- Run external domain-pack code out-of-process. Rationale: Q22 selected JSON IPC/CLI workers so external packs can execute without being imported into core; built-in packs stay honest by using the same interface.
- Broker worker side effects through core. Rationale: Q23 selected typed side-effect requests so workers can propose operations without directly touching providers, network, files, budget, project memory, or external tools/agents.
- Use Civitai model/download/AIR links as the strongest image-pack workspace bootstrap path. Rationale: official Comfy Cloud import and Civitai model APIs are reliable enough for model manifests.
- Treat Civitai image/post links as workflow-first when workflow metadata exists, and conditional references only when workflow import fails or metadata is missing. Rationale: the user expects Civitai workflows to be reused, not discarded.
- Classify every reference link by `source_kind`, `intent_role`, `reproducibility_confidence`, and `workflow_importability` before execution. Rationale: creator references may be style, identity, structure, source-edit, workflow, asset, or exact-reproduction requests.
- Encode workflow changes as typed, family-labeled graph patches over the imported workflow. Rationale: this allows current examples like LoRA, ControlNet, IPAdapter, SAM, detailers, upscalers, and custom nodes while keeping the design open to other supported Comfy capabilities.
- Run validated graph patches automatically after original/patched workflow validation passes. Rationale: Q7 selected autopilot; only cost, credentials, unsupported capabilities, policy/rights, and genuine creative ambiguity interrupt the run.
- Ask ambiguity questions through a creator-facing localhost questionnaire. Rationale: the user explicitly rejected developer-language questions; the harness should ask about visual goal, target use, design elements, references, examples, brand/product constraints, and acceptable changes in creator terms.
- Start each workspace with one lightweight `initial_brief`, then ask only `targeted_followup` questions when ambiguity or risk gates remain. Rationale: Q8 selected initial brief plus need-based follow-up, preserving execution-harness autonomy while giving the planner enough creative context.
- Include `budget_envelope` in the initial creator brief and allow automatic execution only inside that envelope. Rationale: Q9 selected workspace-level budget approval, preserving Q7 autonomy without silent Cloud-credit or Buzz spend.
- Store live provider credentials through a `ppt-master`-style local profile and record only `credential_ref` in workspace state. Rationale: Q10 selected the same API-key setup style as `ppt-master`; provider-specific keys such as `COMFY_CLOUD_API_KEY` and `CIVITAI_API_TOKEN` should be loaded from process env or persistent user config, not copied into generated manifests.
- Render each domain output batch into a localhost review surface and saved static artifacts. Rationale: Q11 selected browser comparison/feedback with durable `review_gallery_session.json`, `result_manifest.json`, static HTML, sidecar metadata, `feedback.json`, and proposal cards; the image pack renders this as a gallery.
- Stop each rendered batch at the review surface and make proposal cards advisory until the human chooses an action. Rationale: Q12 selected human-controlled post-result iteration; no automatic post-result rerun/refine/branch/accept continues without saved review action.
- On acceptance, write a full reproducibility package instead of output-only export. Rationale: Q13 selected a final package containing accepted output files, static review page, workflow snapshots, graph patch diff, prompts/settings, provenance, cost/budget summary, and rights/license notes.
- Save project memory only through explicit creator opt-in at acceptance. Rationale: Q14 selected managed project memory; `project_memory_manifest.json` should reference the final package and record selected reuse dimensions, source hash, allowed reuse scope, rights policy, creator-visible label, and deletion support.
- Apply saved project memory only through explicit creator selection in the next workspace initial brief. Rationale: Q15 selected visible memory cards; stored style/brand/workflow/prompt-settings profiles can influence graph planning only after the creator chooses them for the current workspace.
- Share cross-agent continuation through a clean handoff package. Rationale: Q16 selected a manifest/artifact/status handoff that lets another agent resume without consuming chat transcripts, raw secrets, hidden browser state, or unbounded intermediate noise.
- Refresh the clean handoff package only at stable checkpoints. Rationale: Q17 selected checkpoint refresh after initial brief submission, review pause, saved feedback/action, and final package creation; this balances resumability with privacy/noise control.
- Resume from a clean handoff only after a confirmation screen. Rationale: Q18 selected a short "continue this work?" screen showing current status, next action, budget remaining, selected memory refs, and blockers before a resumed agent may spend budget or submit a new job.
- Treat A2A, MCP, and AG-UI as separate boundary ports rather than alternative product cores. Rationale: 2026 sources define A2A for agent-to-agent tasks/artifacts, MCP for tools/data, and AG-UI for frontend/user interaction; the harness core remains Skill+CLI+state manifests.
